# Exporting an existing server

```shell
make build
export TECHNITIUM_HOST=http://dns.example.com:5380 TECHNITIUM_TOKEN=...
./build/tf-technitium -out ./dns                      # everything
./build/tf-technitium -out ./dns -zone home.example.com -type 'zone,record_*'
```

## Flags

| Flag | Meaning |
|------|---------|
| `-host` | The API address. Defaults to `TECHNITIUM_HOST`. |
| `-username` | The user to log in as when there is no token. Defaults to `TECHNITIUM_USERNAME`. The token or password comes from `TECHNITIUM_TOKEN` or `TECHNITIUM_PASSWORD`. |
| `-insecure` | Skip TLS verification. Defaults to `TECHNITIUM_INSECURE`. |
| `-out` | The directory to write to. Defaults to `.`. |
| `-type` | Comma separated resource types to export, without `technitium_`. A trailing `*` matches a prefix, as in `record_*`. |
| `-zone` | Comma separated zones to export, with their records. |
| `-force` | Overwrite the files this export writes. See below. |

Without `-force`, an existing file is an error. With `-force` and no `-type`
or `-zone`, the export also removes files an earlier export wrote that this
one doesn't, such as the records of a deleted zone. It only removes files that
start with the `# Generated by tf-technitium.` line, and it skips the cleanup
if any object couldn't be read.

## Output

| File | Contents |
|------|----------|
| `zones.tf` | Each zone with its `SOA`, zone permissions and DNSSEC signing. |
| `records_<zone>.tf` | The records of one zone. |
| `settings.tf`, `dhcp.tf`, `blocking.tf`, `access.tf`, `apps.tf` | One file per group of resources. |
| `other.tf` | Anything else, such as API tokens. |
| `imports.tf` | An `import` block per resource. |
| `variables.tf` | Variables for the secrets the export doesn't write out. |
| `technitium_versions.tf` | The provider source and `required_version = ">= 1.5"`. OpenTofu checks this against its own version, so 1.6 and later pass. |

A module can only have one `required_providers` block. If a `.tf` or `.tofu`
file of your own in the output directory already has one, `technitium_versions.tf` isn't
written, and a warning tells you to add
`technitium = { source = "ilijamt/technitium" }` to yours.

Resources refer to each other, as in
`zone = technitium_zone.home_example_com.zone`, instead of repeating names.
Import IDs use the short `zone/domain/value` form unless a value needs JSON.

## After the export

Every value is read through the provider, so a plan right after the export
shows no changes apart from secrets.

- Secrets such as user passwords, TSIG shared secrets and the SSO client
  secret become sensitive variables. The server never returns some of them,
  user passwords among them, so the first apply sets them from your
  variables.
- Apps are exported without `url`, because the server doesn't say where an app
  came from. Add a `url` later to update the app from it.
- An `app_config` is written out in full. When its keys or values look like
  secrets (passwords, tokens, connection strings), the export warns and puts a
  comment above the resource, so keep `apps.tf` private.
- Exported users get `prevent_destroy`, so an account like `admin` can't be
  deleted by accident.
- The built-in groups can't be deleted or renamed, so they're written as
  `data "technitium_group"` blocks. SSO users belong to the SSO provider and
  are written as `data "technitium_user"` blocks.
- Permissions are written in full, `user_permissions = []` included, so
  the configuration owns each section's lists.
